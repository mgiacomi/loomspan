# PR 27 - Framework-owned plan identity and accepted-attempt lineage

## Status

Proposed framework ticket. This is a producer prerequisite for the plan-related
MCP and `loomspan-runtime-debugging` skill work in the LLM trace-understanding
roadmap.

## Outcome

Make the existing `planId` a framework-owned identity for one recorded accepted
plan and all of its updates. Record the accepting model attempt and planning
retry sequence on `PLAN_CREATED` so plan evolution and its validation history
can be reconstructed through explicit identifiers rather than model-authored
values, frame-placement heuristics, or sequence inference.

Do this without adding a second `planInstanceId` concept.

## Why this ticket exists

The developer workflow that exposed the problem is:

> I ran `handleIncident`. Pull up the trace and show me what plan the model
> ended up coming up with for the primary mission.

The current trace contains the needed plan versions, but the relationships are
not producer-guaranteed:

- the planning prompt asks the model to return `"planId": "<unique string>"`;
- `ExecutionPlan` validates only that this value is nonblank;
- `PLAN_CREATED` and `PLAN_UPDATED` copy that model-authored value into record
  metadata;
- plan record placement is selected by scanning the active frame stack for a
  planning frame, then a root-mission frame, then another fallback frame; and
- `PLAN_CREATED` does not record the accepting `attemptId` or
  `retrySequenceId`, even though both are available at the creation call site.

Consequently, duplicate model IDs can merge unrelated plan chains, frame
lineage is doing identity work it was not designed to guarantee, and the link
from validation/retry evidence to the accepted plan is inferential.

The producer must create trustworthy relationships before MCP exposes them and
the skill teaches them. This ticket deliberately precedes any MCP projection or
skill-navigation change.

## Verified current implementation

The implementation context for this work is:

- `DefaultPlanningService.buildPlanningPrompt` asks the model for a unique
  `planId`.
- `DefaultPlanningService.parsePlan` maps model-authored JSON/YAML directly to
  `ExecutionPlan`.
- `ExecutionPlan` requires a nonblank `planId`, and its immutable update methods
  preserve that value.
- `DefaultPlanningService.initializePlanWithQualityChecks` creates one
  `ModelTraceContext` before its semantic-retry loop. Its framework-generated
  `retrySequenceId` therefore spans every planning attempt in that episode.
- `PlanningAttemptResult.modelAttempt()` contains the accepting `attemptId`,
  `retrySequenceId`, attempt number, reason, and provider-attempt number at the
  exact point where the plan is stored and `PLAN_CREATED` is logged.
- `DefaultExecutionTraceRecorder.recordPlanCreated` and
  `recordPlanUpdated` currently emit only `planId` metadata.
- `DefaultExecutionTraceRecorder.recordOnPlanFrame` derives record attachment
  from the active frame stack. Frame attachment remains valuable structural
  evidence, but it is not a plan-chain identifier.
- Nested YAML-skill execution snapshots and restores the session's single plan
  slot. This ticket does not redesign that execution model.

## Identity model after this change

Each existing identifier has one owner and one purpose:

- `retrySequenceId` is generated by the framework for one planning model
  episode and all of its semantic/provider attempts.
- `attemptId` is generated by the framework for one model attempt or proposal.
- `planId` is generated by the framework for the accepted runtime plan and is
  preserved by every mutation recorded as `PLAN_UPDATED`.

The resulting explicit relationship is:

```text
planning retrySequenceId
  -> one or more attemptIds
  -> accepting attemptId
  -> PLAN_CREATED(planId, attemptId, retrySequenceId)
  -> PLAN_UPDATED(planId) ...
```

`planId` is the only plan identity. Do not introduce `planInstanceId`,
`planChainId`, or a retained model-authored plan identifier.

## Required behavior

### Framework-owned `planId`

- Remove `planId` from the plan structure requested in the planning prompt.
- The normal model response contract therefore contains no `planId`. The
  framework adds the field when it materializes an `ExecutionPlan`; keeping the
  field on `ExecutionPlan` does not mean the model continues to supply it.
- Generate a nonblank collision-resistant `planId` inside the framework.
- A `planId` supplied anyway by model output must never be adopted as the
  framework identity. For this ticket, discard/overwrite that property before
  binding the internal candidate and continue with the framework-generated
  value. Do not reject an otherwise valid proposal solely because it contains
  this legacy or unsolicited property. Continue rejecting all other unknown
  fields under the existing strict planning-codec policy.
- The unsolicited value may remain visible only inside the already-recorded raw
  model-response content as untrusted proposal evidence. Do not copy it into
  normalized plan state, plan metadata, a second field, or another retained
  identity concept.
- Preserve the generated ID through `updateTask`, `withActiveTask`,
  `clearActiveTask`, `withStatus`, nested-plan snapshot/restore, and every other
  immutable plan-copy path.
- Emit the same ID in the `PLAN_CREATED` record and every related
  `PLAN_UPDATED` record, including both typed metadata and the normalized plan
  value wherever the current serialized `ExecutionPlan` contains `planId`.
- Two accepted plans must receive different IDs even when their model responses
  are byte-for-byte identical or reuse the same unsolicited model `planId`.

The externally observable lifecycle boundary is acceptance: a rejected
proposal has no recorded plan identity and produces no `PLAN_CREATED`. It is
acceptable for an implementation to allocate and discard an internal candidate
ID earlier if that avoids a new proposal type, provided the ID is not presented
as recorded plan state and can never be supplied by the model.

### Accepted-attempt relationship

- Thread the accepting attempt metadata available from
  `PlanningAttemptResult.modelAttempt()` into the `PLAN_CREATED` recording path.
- Add the accepting `attemptId` and `retrySequenceId` to `PLAN_CREATED`
  metadata.
- Reuse the existing identifiers and validation rules. Do not create another
  planning-episode or acceptance identifier.
- `PLAN_UPDATED` needs `planId`; it does not need the accepting attempt fields
  copied onto every update because callers can join through the corresponding
  `PLAN_CREATED`.
- Preserve the existing attempt/retry metadata on model, validation, retry, and
  quality-warning records.
- Treat the successful planning response's existing attempt map as required at
  the acceptance boundary. If `attemptId` or `retrySequenceId` is absent or
  invalid, fail before storing the plan or emitting `PLAN_CREATED`; do not
  synthesize replacement lineage identifiers in the planning service. The
  production provider-attempt advisor already supplies and validates this map.

### Acceptance and rejection semantics

- A plan stored after ordinary plan-quality retries are exhausted is an
  accepted plan. It receives a framework `planId`, emits `PLAN_CREATED`, and
  retains the applicable `PLAN_QUALITY_WARNING` evidence.
- Deterministic evidence-coverage failure remains a rejection. It throws under
  the current behavior and must not emit `PLAN_CREATED`.
- A proposal that fails validation and is retried remains model-response
  content identified by its `attemptId`; it is not a recorded plan and must not
  share the accepted plan's `planId`.
- Identity establishes recorded relationships, not causality. The framework
  must not claim that a retry fixed a validation issue; that conclusion still
  requires comparison of recorded content.

## Resolved implementation questions

The following decisions are part of this ticket and are not left for code
review to reinterpret:

1. Keep the existing `ExecutionPlan.planId`; do not replace it or add another
   plan identity.
2. Stop asking the model for `planId`. If a response nevertheless contains the
   property, discard/overwrite it and use only the framework value. Other
   unknown fields remain errors.
3. Generate candidate IDs through an internal injectable supplier that defaults
   to UUID generation. Allocation may occur before validation because
   `ExecutionPlan` requires an ID, but rejected candidates never become
   recorded plan state and never emit `PLAN_CREATED`.
4. Reuse the accepting attempt map returned by the provider-attempt path. A
   missing or invalid map is a pre-acceptance failure, not a reason to create
   fallback attempt or retry identifiers.
5. Add the combined plan-lineage topology to the Java producer trace-contract
   coverage in this ticket. Do not add or revise Console fixture corpora here;
   the later MCP/skill work owns its cross-component representative fixture.

## Recommended low-complexity implementation direction

Prefer the smallest internal change that preserves the invariants above:

1. Remove the model-authored `planId` requirement from the prompt and normalize
   the parsed tree by discarding any incoming `planId` and inserting a
   framework-supplied ID before binding it to `ExecutionPlan`. Leave strict
   handling of every other unknown field unchanged.
2. Keep `planId` on `ExecutionPlan` so its existing immutable update operations
   naturally preserve the identity. Audit every constructor/copy path.
3. Add a `Supplier<String>` to the existing internal/package-private
   `DefaultPlanningService` construction path. Production construction uses
   `UUID.randomUUID().toString()`; focused tests inject deterministic distinct
   values. Validate every supplied value as nonblank. Do not publish the
   supplier as a Spring bean, supported SPI, or application configuration.
4. Extend the internal plan-created logging/recording call chain to accept the
   already-available attempt metadata, require its existing validated
   `attemptId` and `retrySequenceId`, and copy only those required relationship
   fields into record metadata.
5. Continue recording plan content through the existing trace recorder; no new
   record type or artifact component is required.

A separate proposal DTO is allowed if it materially improves correctness, but
it is not a requirement. Do not add it solely to make the design appear more
layered. Conversely, do not use a model-controlled or constant sentinel value
as a temporary `planId` if it can escape into stored state or trace evidence.

## Trace contract after this change

For `PLAN_CREATED`:

```json
{
  "recordType": "PLAN_CREATED",
  "metadata": {
    "planId": "<framework-generated>",
    "attemptId": "<accepting-attempt>",
    "retrySequenceId": "<planning-episode>"
  },
  "data": {
    "planId": "<same-framework-generated-value>"
  }
}
```

For every related `PLAN_UPDATED`:

```json
{
  "recordType": "PLAN_UPDATED",
  "metadata": {
    "planId": "<same-framework-generated-value>"
  },
  "data": {
    "planId": "<same-framework-generated-value>"
  }
}
```

Other existing plan fields are omitted from these examples. Metadata/data
agreement for `planId` is required.

## Tests

Add or update focused tests in the planning, state, trace-recorder, and
end-to-end trace contract suites.

### Identity ownership

- A model response without `planId` parses and can become an accepted plan.
- The accepted plan receives a nonblank framework-generated `planId`.
- An unsolicited model `planId` is discarded/overwritten, does not by itself
  reject an otherwise valid response, and is never the recorded framework ID.
- Other unknown model fields remain rejected by the strict planning codec.
- Two identical accepted model responses receive distinct plan IDs.
- All immutable plan update operations preserve the original framework ID.
- Nested plan snapshot/restore preserves each accepted plan's own ID.

### Recorded chain

- `PLAN_CREATED.metadata.planId` equals `PLAN_CREATED.data.planId`.
- Every update for that plan carries the same metadata/data `planId`.
- A separate accepted nested or sequential plan receives a different ID even
  when the model emits identical content.
- The chain remains reconstructable without relying on frame attachment or
  route names.

### Validation and retry lineage

- A validation failure followed by an accepted retry produces:
  - rejected and accepting attempts with different `attemptId` values;
  - one shared planning `retrySequenceId`;
  - validation/retry records linked to that retry sequence; and
  - `PLAN_CREATED` linked to the accepting `attemptId` and the same
    `retrySequenceId`.
- The rejected proposal produces no `PLAN_CREATED`.
- Exhausted ordinary plan-quality errors produce warning evidence followed by
  an accepted, identified `PLAN_CREATED`.
- Deterministic evidence-coverage failure produces no `PLAN_CREATED`.
- A successful planning response with missing or invalid attempt context fails
  before plan storage and produces no `PLAN_CREATED`; no fallback lineage ID is
  created.
- Focused planning test doubles return a valid attempt map matching the
  production `ModelTraceContext` shape instead of relying on empty response
  context.

### Regression coverage

- Plan execution and plan-update behavior remain unchanged apart from identity
  ownership and the new relationship metadata.
- Trace serialization remains valid NDJSON.
- The execution journal and live activity projections continue to recognize
  plan records.
- No new type is added to the supported application-facing Java API allowlist.
- A Java trace-contract scenario covers primary and nested or sequential
  accepted plans, identical proposal content, one rejected proposal,
  cross-frame plan updates, and accepting-attempt/retry linkage. Console fixture
  changes remain outside this producer ticket.

## Acceptance criteria

1. The planning prompt no longer delegates plan identity to the model.
2. The model cannot choose or override the recorded `planId`.
3. Every `PLAN_CREATED` has one nonblank framework-generated `planId`.
4. Every `PLAN_UPDATED` in that chain preserves exactly the same `planId`.
5. Independently accepted plans have distinct IDs regardless of model output.
6. `PLAN_CREATED` records the accepting `attemptId` and planning
   `retrySequenceId`.
7. The identifiers mechanically join accepted plan state to its attempt/retry
   evidence without using frame placement or ordering as identity.
8. Rejected proposals never produce recorded plan state.
9. Quality-warning acceptance and deterministic evidence-coverage rejection
   retain their distinct existing behavior.
10. Relevant module tests and `LoomspanPublicSurfaceArchitectureTest` pass.
11. The normal planning response schema contains no `planId`; an unsolicited
    value is discarded/overwritten while other unknown fields retain strict
    rejection behavior.
12. Missing or invalid accepting-attempt context prevents plan storage and
    `PLAN_CREATED` rather than creating synthetic lineage.

## Guardrails

- Keep one plan identity named `planId`.
- Keep the change inside implementation packages; do not add supported Java API
  or an SPI.
- Do not infer or record a server-generated claim that validation was fixed.
- Do not generate fallback `attemptId` or `retrySequenceId` values at plan
  acceptance. Reuse the identifiers produced for the actual model attempt.
- Do not make frame placement part of the identity contract.
- Do not redesign `recordOnPlanFrame` unless a separate demonstrated defect
  requires it.
- Do not redesign the session's single-plan slot, nested snapshot/restore, or
  concurrency model in this ticket.
- Do not add MCP fields, Console projections, skill prose, or compatibility
  governance here.
- Do not add a plan-chain aggregate or convenience query.

## Out of scope

- MCP typed-fact projection for the new producer-owned relationships.
- Changes to `loomspan-runtime-debugging` skill discovery or workflow guidance.
- Semantic record-content references and inline-content budgets.
- Primary-root selection and frame-tree projection changes.
- Cross-run comparison.
- Parallel sibling-mission support.
- Compatibility guarantees for unreleased trace revisions.

## Follow-on dependency

After this ticket lands, the MCP/skill work can treat producer-recorded facts as
authoritative:

1. select the primary `PLAN_CREATED` through root and planning-frame structure;
2. follow its framework-owned `planId` across every `PLAN_UPDATED`, independent
   of record frame placement;
3. join `PLAN_CREATED.attemptId` to the accepting model attempt; and
4. join `PLAN_CREATED.retrySequenceId` to validation, retry, warning, and
   rejected-attempt evidence.

For artifacts produced before this change, mission lineage plus the old
model-authored `planId` may be used only as a degraded heuristic with ambiguity
stated explicitly. Supporting that fallback in MCP or the skill is a follow-on
product decision, not part of this producer ticket.
